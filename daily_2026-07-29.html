FusionML: Prefill, Not Decode — Mechanism and Boundaries of CPU+GPU Co-Execution on Unified-Memory Apple Silicon

Apple Silicon 把 CPU/GPU/Neural Engine 用统一内存架构 (unified memory) 拼在一起, 一个 transformer 的算子 (matmul 的若干行) 能不能同时让 CPU 跟 GPU 一起算? 之前几次尝试要么没效果, 要么数据精度被混了, 看起来"白干". 这篇 paper 抓到真凶: MLX 的 lazy-graph scheduler 一旦发现"CPU-stream 要吃的输入还没在 GPU 上 materialize"就直接串行化, 一个本来 1.38 倍快的 row-split matmul 在 lazy graph 里反而变成 0.66 倍. FusionML 改成"per-layer + contention-aware"的 CPU+GPU 行拆分, Llama decoder-block prefill 实测加速 1.15-1.38 倍; 真打 Qwen2.5-7B 端到端, time-to-first-token 也提速 1.18-1.25 倍, 而且输出 token 跟 decode 吞吐完全不变. 同时把 decode / ANE / 精度匹配训练这几条死路清楚量化了, 给出 FusionML 在哪些场景"别上"的边界.

📖 专业版问题讲解 (展开)
Apple Silicon 统一内存架构上跨 CPU/GPU 共执行 transformer prefill 的方案. 作者发现 MLX lazy-graph 调度器在 CPU 操作输入未物化时强制串行, 是之前工作失败的根因. FusionML 通过在每层 eager-materialization 边界 + contention-aware row split ratio, 把"per-layer CPU+GPU row 拆分"做到了"无回归 + 1.18-1.25 倍 TTFT 提速"的水平. 5 个 Apple Silicon 芯片 (M1/M2/M3 Pro/M4/M4 Pro) 都能拿到这个提速, 7B checkpoint 输出 token-identical. 同时给出明确的方法边界: decode 不会受益 (带宽共享限制), 精度匹配训练会掉 (0.86-0.97 倍), ANE 因 dispatch overhead 排除.
⚙️ 方法：作者给的是三层叠加的修复方案. 第一层: 在跨 CPU 与 GPU 流之间插入 eager materialization 边界, 把那个因为惰性求值图 (lazy graph) 而被隐式串行化的路径彻底切断, 让 CPU 与 GPU 之间真的能并行跑, 不会再被调度器悄悄拉回串行. 第二层: 用按形状 (per-shape) 测出来的 contention-aware 切分比例, 而不是按"单独跑 CPU 或单独跑 GPU"的理论峰值去盲选切分点. 第三层: 引入一个 runtime gate, 内含 probation 试用 + 周期性重新探测 + 滞后三段逻辑, 把 baseline 单跑模式当作 gate 的一个分支, 任何带来的提速低于 1.18 倍阈值的方案自动降级回 baseline. 整套方案配套一个严格的复现验证协议, 模型权重 / prefill 配置 / chip 尺寸全部公开, 让社区能在多颗芯片上复现同一组数字.
⚖️ 取舍：收益的边界比看起来要硬. 共享内存带宽把 decode 阶段直接挡在门外, 精度匹配的训练也是反向吃亏, ANE 因为操作系统层面的 dispatch 开销太大, 在逐层 (per-layer) 粒度下基本不可用. runtime gate 在内存压力大的时候会变成自伤 — 它不断去探测替代模式, 而探测动作本身会把当前正在跑的那个模式的工作集挤出去, 等于好心办坏事. 实操经验: 跨 CPU 加 GPU 共执行必须先把 eager 边界立稳, 不能假定惰性求值图会帮你调度, 这是多次失败案例总结下来的核心教训.
📊 效果：在五颗芯片 (苹果 M1 / M2 / M3 Pro / M4 / M4 Pro) 上跑 Llama 形状的 decoder-block prefill, 加速幅度落在 1.15 倍到 1.38 倍之间, 而且串到 32 个 block 的完整深度后这个加速幅度不变. 用真 70 亿参数的 Qwen2.5-7B checkpoint 端到端跑, 首 token 时间 (TTFT) 提速 1.18 到 1.25 倍, 同时输出的 token 跟单跑 GPU 时 token-identical, decode 阶段的吞吐也完全不变. 失败场景也被严格量化: 解码阶段 (decode) 因为跟 prefill 共用内存带宽所以不吃这套提速; 精度匹配的微调训练 (precision-matched training) 在五颗芯片上反而掉到 0.86 到 0.97 倍; 神经网络引擎 (Apple Neural Engine, ANE) 因为 dispatch overhead 被排除; 在内存压力大的情况下 runtime gate 自身的探测会把当前 mode 的工作集挤出缓存.

X-Stage: An Overlooked Pipeline Stage for Communication–Computation Overlap in DiT Inference

分布式 Diffusion Transformer (DiT) 推理里, GPU kernel 自己发起跟其他 GPU 的 remote store (把数据直接写到对端内存里) 跟本地的 Tensor Core 计算能不能同时跑? 之前做法一般调度 "什么时候发" + "什么时候收"两步, 但没人管"发完之后, 远端还没看完之前, 发送方还能往前推多少". 8 GPU 节点实测: 短促的 remote-store 突发, 发送方能接着算; 但高频持续的注入会耗尽 outstanding capacity, 反过来顶住后面要发的请求 — 这就叫 backpressure. X-Stage 抓住这个被忽略的"发完之后等远端可见"中间阶段, 用一个三参 Burst–Gap 模型 (backpressure-free issue time + effective drain rate + outstanding capacity) 直接预测 issue 开销跟回压触发时机. 真实收益: DeepGEMM MegaMoE kernel 用 84 组配置测下来, geometric-mean 1.18 倍 / 最大 1.62 倍 kernel 加速; Ulysses sequence-parallel attention 通过 tile-granular 融合 post-attention All-to-All + FlashAttention, FlashAttention-3/4 sender-visible 峰值 1.43 / 1.42 倍加速.

📖 专业版问题讲解 (展开)
提出"X-Stage"作为 comm-compute overlap 里被现有系统忽略的"post-issue, pre-remote-completion"中间阶段. 8-GPU 节点上 NV 新一代架构实测给出 1.18 倍 (MegaMoE) / 1.43 倍 (FlashAttention-3) 加速. 三参 Burst–Gap 模型量化 backpressure 触发, 引导 kernel fusion 设计: 把 DeepGEMM MegaMoE 的 Linear-1/Linear-2 跨 expert wave 交错, Ulysses All-to-All tile-granular 跟 FlashAttention 后半部分融合, 都把计算插在两轮 remote-store 突发之间.
⚙️ 方法：作者一共做了四步. 第一步: 把"X-Stage"建模成三个参数. 第一个参数是无回压情况下连续发起远程写所需时间 (t_free); 第二个参数是远端实际把数据取走的速率 (drain_rate); 第三个参数是节点上能同时挂起的远程写条目上限 (outstanding capacity). 第二步: Burst-Gap 模型, 突发远程写长度小于 t_free 时基本无回压, 一旦突发长度超过 t_free 就把后续 burst 整体往后推, 给远端留出消化时间. 第三步: 两类 kernel fusion 设计. 第一类是 DeepGEMM 框架下的 MegaMoE, 把 Linear-1 和 Linear-2 两段计算交错放在两个远程写突发之间, 既隐藏了写延迟又不让回压形成. 第二类是把 Ulysses 序列并行的 All-to-All 跟 FlashAttention 在瓦片粒度融合, 让输出瓦片的主人提前发远程写, 不需要单独的通信 warp 或 SM 单元. 第四步: 在 84 组 MegaMoE 配置加多个 FlashAttention 版本上做实测.
⚖️ 取舍：X-Stage 不是免费的午餐. 短促突发的远程写没问题, 一旦变成持续高频注入触发回压, 之前定好的整段调度表全部要重排. 真实部署里, 突发检测加模式切换必须有回调钩子接到 runtime 里去, 跟"随便插一句 device-initiated remote store 就能 overlap"那种简单做法完全不在一个复杂度级别. 调度器的可观测性必须跟得上, 否则发现 backpressure 时已经晚了.
📊 效果：DeepGEMM MegaMoE kernel 在 84 组配置上的几何平均加速是 1.18 倍, 最大加速 1.62 倍, 比 Expert-Wave baseline 实测都赢. Ulysses 序列并行加上 FlashAttention-3 后, 发送方视角最大提速 1.43 倍; 配上 FlashAttention-4 最大提速 1.42 倍. 把序列拉长以后, 整体稳态运行时间逐步向"只跑 FlashAttention 本身"的理论下限靠拢, 说明这套做法把通信延迟真的藏进了计算里.

Denial of Deadline: Network-Driven Accuracy Collapse in Distributed Inference Pipelines

现代 edge-cloud AI 推理通常这么干: 简单请求本地小模型"快路径"秒回, 难请求丢到云上更大模型"慢路径"拿高准头结果, 协调层做"router 路由 + merger 合并". 这篇 paper 第一作者是 Tavori, 通讯作者之一 Ion Stoica (UC Berkeley RISELab) 直接下场打"攻击面": bad guy 拿合法请求凑出 Yo-Yo 突发 (一会儿 100 倍 burst, 一会儿 0), 把 cloud autoscaling / edge gateway / 远端 HBM 的共享资源全顶满, 让慢路径用户在 deadline 之后才拿到结果. merger 直接丢掉迟到的"高质量协助", fast path 还能秒回 — 表面上服务可用, 实际慢路径精度全部白扔, 这就是"accuracy collapse". 实测在 edge-cloud 自动驾驶双层 multi-object tracking 管道里: 约 4000 个 burst 请求把慢路径 p99 延迟从 92 ms 顶到 2 秒, Object Tracking 精度平均下降 7.0 HOTA; 攻击视频段不一样, 不同类别衰退 2.0-18.7 HOTA 不等. 直接呼吁攻/防都要加到 routing + merging + admission control + 资源隔离的协议栈上.

📖 专业版问题讲解 (展开)
fast-path + slow-path + coordination layer 的分布式推理被 IoT 突发 "Yo-Yo" 攻击打爆"accuracy collapse"问题. 作者通过 edge-cloud 自动驾驶 pipeline 实测量化: 慢路径 p99 延迟从 92 ms 拉到 2 秒, MOT 精度下降 7.0 HOTA (不同类 2.0-18.7), 缓解依赖 routing + merging + 资源隔离. 新攻击面: 共享 slow-path 资源 (edge link, gateway, cloud autoscaling 限流) 都成了"网络拉胯推动精度崩溃"的杠杆.
⚙️ 方法：作者一共做了四步. 第一步是把整套推理架构形式化成三段: 快路径 (fast path, 端侧小模型秒级响应), 慢路径 (slow path, 云端大模型或高算力后端算出更准结果), 还有协调层 (coordination layer, 拆出 router 路由决策 + merger 合并决策两个职能). 第二步是攻击建模: 攻击者只控制合法请求的内容和时间, 凑出 Yo-Yo 突发 (一会儿 100 倍突发流量, 一会儿 0 流量), 把 cloud autoscaling 瓶颈、edge 网关、远端高带宽内存这些共享资源全部打满, 让慢路径的请求超出合并端设定的期限 (deadline). 第三步是仿真层面用 burst 请求触发资源争用, 推到 merger deadline 之外. 第四步是把整套机制放进真实的边云两层多目标跟踪 (multi-object tracking) 管道里实测, 用 HOTA 指标 (Higher Order Tracking Accuracy, 同时衡量检测 + 关联的综合跟踪精度) 作为准确度量化标准.
⚖️ 取舍：传统的防御思路 (监控端点可用性, 拉防火墙) 完全抓不到这个问题. 服务可用度高, 用户看着一切正常, 但实际慢路径的精度被偷偷消耗掉. 真正能缓解这类问题必须在路由准入控制 (admission control) + 慢路径资源隔离 + 合并器严格 deadline 执行这几层都加上防护, 但每多一层防护都会增加尾部延迟成本. 实际部署的 AI Infra 服务很难白嫖这一整套保护, 要么花钱, 要么承担精度波动.
📊 效果：大约 4000 个突发形状的请求把慢路径的尾延迟 (p99 percentile latency) 从 92 毫秒硬拉到 2 秒. 多目标跟踪精度平均下降 7.0 HOTA, 不同攻击视频段差异很大, 衰退范围在 2.0 到 18.7 HOTA 之间. 数据集中罕见类别 (比如停止标志) 几乎损失掉攻击前一半的预测准确率. 整篇论文的实证显示: 边云多层共享慢路径资源构成了新型攻击面, 端点可用性指标完全抓不到这种精度崩溃.

Libra: Taming Attention Workload Skew in Long-Context LLM Training with Bounded Sequence Pool

长上下文 LLM 训练有个老问题: 每个 sample 拿固定 token 数塞进 packed sequence, 对 attention (它的开销跟"序列长平方"成正比) 来说完全不均衡 — 一个长文档跟 100 个短句拼起来, attention 工作量能差一个数量级. 整条训练 pipeline 的瓶颈卡在最长序列, GPU 大部分 cycle 在等最长那条做完. Libra 是中国科学院 / 阿里 / NUS 团队给的方法: 把序列拉到一个"bounded sequence pool"里, 按 attention length (实际平方 cost) 而不是 token count 去平衡, 用 bounded-pool 策略保证 attention 短板不超 1.5x. 公开实验: normalized cluster throughput 接近 ideal linear scaling (16x 集群 vs 单卡), 跟当下常用的 sequence packing baseline 比结束时间缩短数个 epoch.

📖 专业版问题讲解 (展开)
Bounded sequence pool + 按 attention-cost 而不是 token-count 平衡, 解决 packed-sequence training 里 attention 工作量长尾不平衡. 来自 UCAS + 阿里 + NUS 的训练 infra 团队, normalized cluster throughput 跑到 ideal linear scaling (16 卡 vs 单卡), 解决长上下文训练里被最长序列卡 GPU 的老问题.
⚙️ 方法：作者一共做了四步. 第一步是把平衡单位从"token 数量"换成"注意力开销的代价"(实际就是样本序列长度的平方和), 让 packing 不再按字数均衡而按算力均衡. 第二步是引入 bounded sequence pool 这个核心抽象, 池子里最长跟最短的 attention cost ratio 严格控制在 1.5 倍以内, 杜绝一个超长序列拖垮全卡的场景. 第三步是把训练调度、数据预取、池子刷新这一整套流水线同步调整, 不是简单改个 sampling distribution 就完事. 第四步是用真实 16 卡集群做长上下文预训练实测, 跟当下常用的 sequence packing baseline 做严格对照.
⚖️ 取舍：Bounded sequence pool 选那个 1.5 倍的 attention cost 上限本身是个取舍点. 选得太严 (1.3 倍以下) packing 收益直接缩水; 选得太松 (2 倍以上) 长尾问题又冒头, 等于没解决问题. 真实部署必须根据模型特性用自动调参工具搜最优值, 不能直接抄一个默认值. 此外这套方案要重写训练数据加载器 (dataloader), 不是简单在调度器里挂个钩子就能完成, 改造成本跟现有训练代码库强相关.
📊 效果：归一化的集群吞吐量 (normalized cluster throughput) 跑到了接近理想线性扩展的水平, 16 卡集群对比单卡的吞吐比基本贴近 16 倍理论值, 比 sequence-packing baseline 改善显著. 长上下文训练每个 epoch 完成时间跟现有最优基线相比缩短明显, 短序列所在的 GPU 不再被最长那条序列的 stall 拖累. 整张图表基本跟理想线性扩展那条参考线贴合.

SpecBox: Speculative Sandbox Scheduling for Efficient LLM Agent Serving

新一代 LLM agent 通过 Model Context Protocol (MCP) 启一堆独立 sandbox 跑外部工具 (代码执行 / 浏览器 / 数据库). 当前"pre-warm 长期预留 sandbox"浪费内存, "lazy on-demand 启动"冷启动秒级延迟. SpecBox 思路: 在 LLM 还在出 token 的时候用 keyword matching + 语义 embedding 推下一个 sandbox 要什么工具, 用 sandbox 依赖图"预先把下一次 sandbox 拉起来 + 切好工具栈". 同时开两条旁路: 一是语义缓存剪掉重复 sandbox 调用 (用户跑过的同一个 SQL 不再启 sandbox), 二是 out-of-band shared-memory 通道走 zero-copy artifact transfer (不绕常规 network stack). 高并发多轮 agent trace 实测: P99 端到端延迟降 2.9 倍, 峰值内存比"长留 sandbox"省 45.9%.

📖 专业版问题讲解 (展开)
LLM agent 跑 MCP 外部 sandbox 时的 speculative 调度. Beihang + Leeds + Sydney 团队. 实测 P99 E2E latency 降 2.9x, peak memory 减 45.9% vs long-lived sandbox. 关键点是"speculative prewarm + 语义 cache + shared-memory bypass"三件套, 解决 agent tooling 调度的 tail latency 跟内存浪费问题.
⚙️ 方法：作者给了四招组合拳. 第一招叫投机性 sandbox 预热: 在模型生成 token 的过程中, 系统同时跑关键词匹配加流式语义嵌入, 提前判断下一个 sandbox 大概要跑什么工具, 把 sandbox 的引导流程 (拉镜像、加载文件系统、配命名空间、握手 runtime) 跟模型推理完全 overlap 起来, 不再是模型停下来等工具准备. 第二招是上下文相关的随机预取: 系统维护一张 sandbox 依赖关系图, 用概率方式预测接下来几步会切到哪个 sandbox, 把预热时间窗从一步延伸到多步. 第三招是语义结果缓存, 把用户反复调用的同一个工具调用结果缓存起来, 直接复用而不再起一个新的 sandbox. 第四招是 out-of-band 共享内存传输通道, sandbox 之间传数据走零拷贝路径, 不绕常规网络栈.
⚖️ 取舍：投机性预取本质上是在赌下一步的依赖关系, 赌错了就是浪费 — 启动了根本用不上的 sandbox. 实操里这套机制对常见 agent 模式友好, 命中率高的"热门工具栈"回本快; 但长尾冷门工具占比高的场景, 预热收益会下降. 另外 out-of-band 共享内存通道假定 sandbox-host 之间共享内存, 跨物理主机部署时这套零拷贝路径就不成立, 要重新设计跨主机的传输层.
📊 效果：高并发多轮的 agent trace 实测下来, P99 端到端延迟比"按需启 sandbox"基线降 2.9 倍; 跟"永久预留 sandbox"基线比, 峰值内存消耗降低 45.9%. 多轮 agent 切换时, sandbox 引导跟大模型 token 生成全程并行不互卡, GPU 不再被工具启动延迟阻塞.
